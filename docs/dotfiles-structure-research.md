## Assessment of this PR

**Repository facts:** the [root README](../README.md) separates historical macOS v1 from planned PAW v2 and Omarchy profiles. The [v1 README](../profiles/macos/v1-yabai/README.md) distinguishes reconstructed provenance from a complete point-in-time backup. [Validation](../scripts/validate.py) checks 60 snapshot files and the original 221 legacy files against recorded hashes/Git blobs, rejects snapshot symlinks, and blocks common private paths. The [public-repo rules](public-repo-rules.md) exclude all SSH configuration and machine state.

**Recommendation:** retain explicit, self-contained profiles and immutable history. A snapshot records selected bytes and provenance; deployment additionally requires destination ownership, dependencies, collision handling, application lifecycle and rollback. Two empty future profiles provide no evidence that shared layers or a manager would simplify real differences. Reconsider when two maintained profiles repeatedly need the same changes, rather than deduplicating the archive.

## Four contrasting repositories: facts and useful ideas

- **holman/dotfiles — topic-centric classic, with observed 2026 activity.** Its [README](https://github.com/holman/dotfiles/blob/9a90082b61fa5659789b9d41544c19098825a3ca/README.md) groups shell fragments and installers by topic. [Bootstrap](https://github.com/holman/dotfiles/blob/9a90082b61fa5659789b9d41544c19098825a3ca/script/bootstrap) discovers `*.symlink`, offers collision choices, then invokes further Mac setup; [install](https://github.com/holman/dotfiles/blob/9a90082b61fa5659789b9d41544c19098825a3ca/script/install) runs Brew Bundle and discovered installers. [Latest inspected commit: June 25](https://github.com/holman/dotfiles/commit/9a90082b61fa5659789b9d41544c19098825a3ca). **Takeaway:** component-oriented documentation and explicit conflict handling are useful inside a future profile. Avoid automatic discovery/execution across this repository: it contains mutually exclusive desktops and archives.

- **mathiasbynens/dotfiles — explicit fresh-machine operations.** The [README](https://github.com/mathiasbynens/dotfiles/blob/b7c7894e7bb2de5d60bfb9a2f5e46d01a61300ea/README.md) presents bootstrap, macOS defaults and package installation separately. [Bootstrap](https://github.com/mathiasbynens/dotfiles/blob/b7c7894e7bb2de5d60bfb9a2f5e46d01a61300ea/bootstrap.sh) pulls upstream and broadly copies with rsync exclusions; [brew.sh](https://github.com/mathiasbynens/dotfiles/blob/b7c7894e7bb2de5d60bfb9a2f5e46d01a61300ea/brew.sh) upgrades packages and changes the login shell. [Latest inspected commit: April 9, 2024](https://github.com/mathiasbynens/dotfiles/commit/b7c7894e7bb2de5d60bfb9a2f5e46d01a61300ea); treat it as a classic example, not a current installation recipe. **Takeaway:** keep setup stages reviewable; replace broad copy/exclusion logic with explicit allowlists. Its [.bash_profile](https://github.com/mathiasbynens/dotfiles/blob/b7c7894e7bb2de5d60bfb9a2f5e46d01a61300ea/.bash_profile) demonstrates optional local extensions and late overrides without requiring a framework.

- **twpayne/dotfiles — actual multi-machine chezmoi.** [.chezmoiroot](https://github.com/twpayne/dotfiles/blob/13f4e5f23cb8333a263efec7cab3a324d5a37007/.chezmoiroot) restricts deployment source to `home`; the [configuration template](https://github.com/twpayne/dotfiles/blob/13f4e5f23cb8333a263efec7cab3a324d5a37007/home/.chezmoi.toml.tmpl) derives shell, work/personal and headless flags, while [ignore logic](https://github.com/twpayne/dotfiles/blob/13f4e5f23cb8333a263efec7cab3a324d5a37007/home/.chezmoiignore.tmpl) filters by OS and features. [Latest inspected commit: November 5](https://github.com/twpayne/dotfiles/commit/13f4e5f23cb8333a263efec7cab3a324d5a37007). **Takeaway:** a deployment root separate from documentation/history and explicit feature selection scale to real machine differences. Its [installer](https://github.com/twpayne/dotfiles/blob/13f4e5f23cb8333a263efec7cab3a324d5a37007/install.sh) immediately applies configuration; that coupling is unsuitable for this archival PR. Do not import its personal/private integrations.

- **folke/dot — current modular workstation automation.** [Latest inspected commit: April 17, 2026](https://github.com/folke/dot/commit/10526a848771bab9e9fbb98b5995c997f7ef92b6). Its [playbook](https://github.com/folke/dot/blob/10526a848771bab9e9fbb98b5995c997f7ef92b6/ansible/playbook.yml) separates packages, dotfiles, user, apps and system roles. The [dot role](https://github.com/folke/dot/blob/10526a848771bab9e9fbb98b5995c997f7ef92b6/ansible/roles/dot/tasks/main.yml) links individual top-level config directories; [.gitignore](https://github.com/folke/dot/blob/10526a848771bab9e9fbb98b5995c997f7ef92b6/.gitignore) excludes generated theme/session artifacts. Its [inventory](https://github.com/folke/dot/blob/10526a848771bab9e9fbb98b5995c997f7ef92b6/ansible/hosts) is localhost, so this is modularity evidence, not a verified multi-host implementation. **Takeaway:** separate configuration deployment from system provisioning; adopt neither its broad linking scope nor host-specific package choices.

## Deployment approaches and boundaries

| Approach | Source facts | Recommendation here |
| --- | --- | --- |
| Reviewed copies | Current profile instructions require backup and selected copies. No manager is required. | Best fit for historical restoration; document how later live edits return through review. |
| GNU Stow | Symlink manager; tree folding can link an entire directory. `--no-folding` creates real directories with links beneath them. `--simulate --verbose` previews operations; existing unmanaged files normally conflict. `--adopt` moves destination contents into the package. [Manual source](https://github.com/aspiers/stow/blob/891c187b73d4654ec9800647af06f0cfd880e2fe/doc/stow.texi). | Candidate for stable, user-authored future configuration. Select one explicit package and target; preview, back up and resolve conflicts first. Never adopt into frozen snapshots. |
| chezmoi | Generates ordinary destination files by default; [templates and ignores](https://www.chezmoi.io/user-guide/manage-machine-to-machine-differences/) express machine differences. [Diff/merge workflow](https://www.chezmoi.io/user-guide/frequently-asked-questions/design/) separates source from live state; [apply](https://www.chezmoi.io/reference/commands/apply/) supports `--dry-run --verbose`. | Useful when several maintained machines need repeated variations or writable destination files. Costs include filename conventions, template/ignore logic and deliberate reconciliation of application edits. Defer migration. |

Git ignore rules are publication rules, not a deployment allowlist. Stow has [separate ignore selection](https://github.com/aspiers/stow/blob/891c187b73d4654ec9800647af06f0cfd880e2fe/doc/stow.texi); do not assume `.gitignore` prevents deployment. Keep archive, inventories and documentation outside any future deployment root. A dry run is a preview, not a backup or application compatibility test.

**Writable applications need individual policies.** [Karabiner's official instructions](https://karabiner-elements.pqrs.org/docs/manual/misc/configuration-file-path/) explicitly require linking the `karabiner` directory rather than `karabiner.json`, because a file symlink breaks change detection. A folded directory could also receive application backups/state in the checkout. Prefer reviewed copies initially; if later linking, isolate an intentional writable directory and exclude generated contents. A blanket `--no-folding` policy would produce the wrong boundary for Karabiner.

The [planned PAW profile](../profiles/macos/v2-paw/README.md) reserves `config.json5` capture, but no public, version-matched contract for settings writes or symlink preservation was verified. Nonpublic implementation details are omitted. **Recommendation:** prefer a regular live file with explicit diff/capture, never a writable link into v1. Before considering links, test settings changes, file replacement and reload behavior against the chosen release. Atomic replacement can break an individual file link; directory links can instead expose the checkout to application writes. Installed PAW behavior remains unverified.

## Adopt now, defer, avoid

**Adopt now:** preserve the 221/60-file boundaries; keep profile status, provenance and restore limits prominent. Define future local overrides per application: exact location, optional/required behavior, load order, precedence and capture exclusion. Public examples contain placeholders; actual host values remain outside the checkout. Avoid inventing a universal override mechanism where the application has none. Existing validation blocks `*.local` and `.local/`, so tracked examples need permitted names; do not weaken privacy rules to accommodate a convention.

**Defer until v2/Omarchy exists:** test application writes/reloads, collision refusal and rollback against a disposable target before selecting deployment tooling. Separate dependency installation, configuration deployment, permissions and service activation. Use a curated Brewfile with reasons and tested versions; [Homebrew](https://docs.brew.sh/Brew-Bundle-and-Brewfile) provides `bundle check`, while installation can upgrade packages. Keep upgrades/cleanup opt-in and never derive desired dependencies from an entire machine dump.

The [current Omarchy manual](https://omarchy.org/manual/dotfiles/) assigns user configuration to `~/.config` and upstream files to `/usr/share/omarchy`. It now lists `hyprland.lua`, `bindings.lua`, `monitors.lua`, `input.lua`, `looknfeel.lua`, `autostart.lua`, `omarchy/shell.json` and foot. **Recommendation:** inventory the installed generation first, track selected overrides plus user-added packages, and preserve upstream update ownership. Neither old `.conf`/Waybar examples nor these current paths establish this unknown host's layout.

**Avoid:** copying someone else's preferences, blanket home linking, automatic installer discovery, premature shared layers, SSH/secrets, and treating successful integrity checks as proof of deployability.

## Small documentation changes adopted in this PR

1. The planned v2 README now has a deployment-policy table: shell files are eligible for linking; Karabiner and PAW require separate writable-config handling and capture review.
2. Planned-profile documentation now specifies a local-override contract, without changing frozen files or implementing hooks.
3. Future profile capture notes must list tested application/Omarchy versions, curated dependencies, destination ownership and rollback verification before calling a profile deployable.

The research and resulting documentation changes leave both snapshots unchanged. No installation, live-home inspection, deployment or runtime compatibility testing was performed during this research.
